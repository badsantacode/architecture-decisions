# 3. Choose LLM (SaaS vs Self-hosted) — final decision

Date: 2026-09-20

## Status

Accepted

Supersedes [2. 2 Choose LLM SaaS vs Self-hosted](0002-choose-llm-saas-vs-self-hosted.md)

## Context

В проекте возникла дилемма: выбрать проприетарную облачную модель (SaaS, GPT-5) или развернуть Open-Source модель (Llama 3) на собственных серверах (Self-hosted).

**Ограничения проекта:**
- **Нагрузка**: 5 RPS (пиковая).
- **Latency**: 10–16 секунд (SLA, PRD 5.1).
- **Privacy**: данные клиентов и внутренние документы не должны покидать периметр компании.
- **Бюджет**: 7.3 млн руб., срок 53 дня.
- **Команда**: нет выделенного MLOps-инженера, DevOps работает part-time.
- **Оборудование**: On-Premise, GPU-сервер.


## Decision

В задании указана **Llama 3**. Для проекта мы выбираем **Llama 3.1 70B** — это та же Open-Source модель от Meta, но с окном контекста **128k** токенов вместо **8k**. Для RAG-системы, где на каждый запрос подаётся **8,000 токенов** контекста из базы знаний, окно 8k почти полностью заполняется, а 128k даёт запас в 16 раз. Это снимает риск обрезки контекста и деградации качества ответов.

Итого: выбираем **Self-hosted Open-Source модель (Llama 3.1 70B) в 4-bit квантовании на 2× A100 80GB**.

Ниже приведены данные для обоснования решения.

### Расчеты
**SaaS GPT-5 для 5 RPS**

За 1 запрос:
- Input: 8,000 токенов × $1.25 / 1M = **$0.010**
- Output: 200 токенов × $10.00 / 1M = **$0.002**

Итого: $0.012

За месяц (24/7):
$0.012 × 5 RPS × 86,400 сек × 30 дней = **$155,520**

**Сравнение по критериям SaaS vs Self-hosted:**

| Критерий | SaaS (GPT-5) | Self-hosted (Llama 3.1 70B, 4-bit) |
| :--- | :--- | :--- |
| **Стоимость (OPEX)** | ~$155,520/мес (5 RPS, 24/7, 8k input / 200 output) | ~$26,800/год (электричество + ЦОД) |
| **Стоимость (CAPEX)** | $0 | ~$40,000 (2× A100 80GB + сервер) |
| **Privacy** | Данные уходят вендору, риск утечки | Данные не покидают периметр |
| **Качество ответов** | Высокое, особенно на сложных рассуждениях | Достаточное для RAG по базе знаний |
| **Latency** | Зависит от сети и загрузки вендора | ~12.5 сек на 200 токенов (L40S x2, 4-bit), укладывается в SLA |
| **Сложность поддержки** | Минимальная | Требует настройки inference, мониторинга GPU |

1. **Стоимость**: GPT-5 при нагрузке 5 RPS обходится в **~$155,520/мес** (более 12 млн руб./мес), что превышает бюджет проекта за 2 месяца. Self-hosted решение стоит **~$66,800 за первый год** (CAPEX + OPEX), что в **2.3 раза дешевле** годового OPEX GPT-5, и окупается с первого месяца.

2. **Privacy**: данные не передаются внешнему вендору, что снимает риск утечки через облачный сервис.

3. **Latency**: расчёт по Roofline Model и данные публичных бенчмарков показывают, что Llama 3.1 70B в 4-bit на 2× A100 80GB генерирует 200 токенов за **~12.5 секунд**, что укладывается в SLA 10–16 секунд. Для сравнения: один запрос к GPT-5 в среднем занимает 10–12 секунд, но при пиковой нагрузке вендор может ограничивать пропускную способность.

4. **Окно контекста**: Llama 3.1 70B имеет окно **128,000 токенов**, что даёт огромный запас для подачи контекста из RAG-системы (8,000 токенов на запрос — это всего 6% от окна).

5. **Независимость от вендора**: нет риска изменения цен, блокировки аккаунта или прекращения доступа к API.

## Consequences

### Positive (Pros)

- **Экономия**: TCO за год (~$67,000) в 2.3 раза меньше годового OPEX GPT-5 ($155,520).
- **Приватность данных**: данные не покидают периметр компании.
- **Предсказуемый OPEX**: фиксированные затраты на электричество и ЦОД, нет переменной цены за токен.
- **Контроль над моделью**: можно дообучать и настраивать под специфику проекта.
- **Окно контекста 128k**: запас для RAG-системы, не нужно экономить на контексте.

### Negative (Cons / Trade-offs)

- **CAPEX на железо**: требуется ~$40,000 на GPU-сервер (2× A100 80GB + платформа).
- **Качество ответов**: Llama 3.1 70B уступает GPT-5 в сложных рассуждениях, что может повлиять на точность ответов по нестандартным вопросам.
- **Сложность поддержки**: нужна настройка inference (vLLM / TensorRT-LLM), мониторинг GPU, обновление модели — дополнительная нагрузка на DevOps.
- **Latency генерации**: ~12.5 секунд на 200 токенов, что требует асинхронной архитектуры (AsyncIO) для обработки параллельных запросов.
- **Риск деградации качества при 4-bit**: квантование может незначительно снизить точность ответов; необходим контроль качества через Golden Set.

### Mitigation Plan

- **Нагрузочное тестирование**: провести бенчмарки (vLLM) для подтверждения 5 RPS при 4-bit квантовании.
- **AsyncIO**: использовать FastAPI + асинхронную обработку для параллельных запросов.
- **Мониторинг**: настроить отслеживание GPU-метрик (загрузка, температура, VRAM).
- **Golden Set**: ручная валидация 100 пар вопрос-ответ для контроля качества после квантования.
- **Резервный вариант**: если качество окажется недостаточным, рассмотреть гибридную схему (SaaS для сложных запросов).

## Alternatives Considered

1. **SaaS (GPT-5)** — отклонено из-за непредсказуемого OPEX ($155,520/мес при 5 RPS), риска утечки данных и зависимости от вендора.
2. **Гибрид (SaaS для сложных запросов, Self-hosted для простых)** — отклонено из-за усложнения архитектуры и двойного контура поддержки при ограниченной команде DevOps.
